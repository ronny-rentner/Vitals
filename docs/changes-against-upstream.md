# What this version changes against upstream Vitals

Compared: upstream `corecoding/Vitals` at `main` (`7108c2a`, metadata version 84) and the branch `catalog-rewrite`, on 2026-10-10.

This file has two parts. Part 1 is what a user of the extension notices, in the words of the settings and the menu. Part 2 is what changed under the hood and how the claims of part 1 were measured; nothing in it is needed to use the extension.

## Part 1: For the user

### What is better

Ranked by what upstream's users ask for: the open issues of `corecoding/Vitals` that a point answers, and how many people reacted to or commented on them (in brackets, counted on 2026-10-08). Points without an issue follow, by how many users they reach.

1. **The top bar can be reordered by drag and drop.** The user drags a sensor in the top bar to where it should be. Upstream shows pinned sensors in the order they were pinned, and people in the request edit the setting by hand. A sensor that is unpinned keeps its place for when it is pinned again. Answers #93 "Reorder indicators" (46), the most supported open request, open since 2019.
2. **Several storage locations.** The menu shows the space of several disks and shares, each in a section of its own, and for a disk also what it read and wrote. Upstream shows one filesystem, the one that holds a path typed into the preferences. Here the preferences list what is mounted, and the user picks from that; `/` is shown from the start. A location has its values whenever something is mounted there. One switch adds the drives GNOME mounts, such as a USB stick, for as long as they are plugged in. A network share is asked for its space at an interval of its own, set in minutes, and not at all while it is not connected, so opening the menu never connects it. Answers #143 "Multiple Storage Locations" (40), with #455 and #503.
3. **The menu's categories can be reordered.** The user drags a category onto another one in the menu, and it takes that place; the preferences list the categories in the same order. Upstream's order is fixed. Answers #451 "Order Menu Components" (25).
4. **The NVIDIA card can sleep.** `nvidia-smi`, which reads an NVIDIA card and keeps it awake, runs only while a GPU value is on screen: pinned to the top bar, or in the open menu. Upstream starts it when GPU monitoring is switched on and keeps it running. Answers #275 "Check if dGPU is awake before polling" (11) and #442 "Option Monitor GPU prevents NVIDIA from going to sleep" (6). Tested with a stand-in for `nvidia-smi`; whether a real card then goes to sleep is not tested.
5. **Only what is shown is read.** A value is read only while it is on screen, from the moment it appears. Upstream reads every value of the menu when the menu opens, and the counters behind its rates on every tick, whether they are shown or not. The price is one second: a rate whose source was not read during the last update interval, such as processor usage, shows "…" until its second reading; upstream's is there the moment the menu opens.
6. **Sensors can be renamed, hidden and shown in the category's header.** A click on a row opens its actions: Pin to top bar, Pin to category, Rename and Hide. They look like the second-level menus of GNOME's quick settings. A hidden sensor is also left out of the average, minimum and maximum, so one that reads nonsense no longer spoils them. Upstream has none of these. Answers #83 "Customize labels" (14) and #222 "Hide unwanted sensors" (8).
7. **The network numbers are right, and the list stays clean.** The totals count only the hardware interfaces, so traffic that also passes a bridge, a container or a VPN is not counted two or three times (#377 "Boot RX is not correct" (7), #319 "combines both Ethernet interface and the Bridge that contains it"). An interface that is gone has no rows any more (#360 "Network Interfaces are not removed", #557 "remembers every single network adapter, including ephemeral ones"). One sensor shows download and upload together (#198 "Combine net up/down in panel" (2)). Only the hardware interfaces are listed; an option brings back the bridges, container and VPN interfaces.
8. **No extra package to install.** Storage space works without installing anything. Upstream needs `libgtop` for it, shows nothing without it, and its README tells users which package to install on each distribution; #421 is about those instructions being wrong for Arch.
9. **Even spacing in the top bar.** Every icon is the same distance from its value and from the next sensor. Upstream's gaps range from 0 to 6 pixels, because its icon files differ and each category is corrected by hand. Answers #505 "Custom spacing" and #398 on the item's position; the closed #41 "Please add indicator spacing" (12) and #141 (14) asked the same.
10. **No stale values.** A sensor that cannot be read is hidden until it can be read again; upstream's row keeps showing its last value. One unreadable temperature no longer empties the average, minimum and maximum.
11. **Voltages are not mixed.** The voltage category no longer has an average, minimum and maximum over all voltages; upstream's put a 17 V battery, a 1.2 V rail and a 5 V USB supply into one number. The header shows the battery's voltage, else the system's, and a USB supply's only when there is nothing else. Relates to #381 "PSU Voltage contaminating Voltage monitoring".
12. **Every battery is shown, and no working sensor is hidden.** Each battery is found by itself, whatever its name, with its own values, also the battery of a wireless mouse or keyboard, which is named after the device. Upstream shows one battery, picked from a list of eight names; that setting is gone. With several batteries that power the machine, the header shows their power rates together; on a desktop whose only battery is a mouse's, it shows that battery's charge. A power rate is negative while the battery discharges; upstream's is always positive. Answers #263 "Display two batteries at the same time" (6) and #540 "Power Rate is always positive even when discharging" (4). Tested with made-up batteries; this machine has one. The option "Skip sensors that read zero" no longer wrongly excludes working sensors. With upstream it can skip a voltage that reads zero when it is found, such as that of an idle USB port, which then stays hidden after something is plugged in. Here it skips only temperatures.
13. **The top bar is made for reading.** Icons and units are lighter and smaller than the numbers; one option switches that off. All digits have the same width, so a value does not jitter as it changes. With the option for fixed widths, the room kept for a value's widest text is given back after a minute; upstream keeps the widest width a value ever had until the extension restarts.
14. **The menu holds still.** It always has the same width; upstream's grows with its widest row. It opens centered under the pointer and stays there while it is open. Upstream puts its left edge under the middle of the top-bar item, which moves as the values change width, and pushes it back in at the screen edge, so where it appears follows no rule a user can see. The option to center it under the item is kept. The open category stays open while the menu is closed, and long and short categories open the same way.
15. **Rows have a fixed order.** Sensors are always in alphabetical order. Upstream has an option to switch sorting off, which then shows them in no meaningful order; the option is gone.
16. **The network category can be read.** It is in sections with plain labels: the machine's speeds, the hardware interfaces ("WiFi (wlp0s20f3) download speed"), the amounts transferred, and, when the option for them is on, the virtual interfaces below a line. Upstream lists "wlp0s20f3 rx", "Device rx", "Boot rx" and "Session rx" in one alphabetical run. In the temperature and fan categories, the average, minimum and maximum stand below a line and can be switched off.
17. **Pins and colours survive a renamed label.** A sensor keeps its pin and its colour rule when the user renames it or a translation changes its label. Upstream drops both.
18. **Units are written the standard way.** `kB`, `kHz` and `kbit/s`: a lowercase k for a thousand, and a slash in every rate. Upstream writes `KB`, `KHz` and, for bits, `Kbps`, next to `KB/s` for bytes.
19. **More sensors.** This version adds the thermal zones, except those already shown as a temperature, the processor's power limit and the ThinkPad lap mode. Two devices with the same name, such as two NVMe drives, each get their own sensor. New hardware shows up the next time the menu opens; upstream finds hardware only when the extension is switched on.
20. **Clearer preferences.** The update interval is picked from a list of eight values; upstream's slider from 1 to 60 makes it hard to hit one second or two, and shows its value in small grey text. A setting's description says what its name does not. A choice between few options is a toggle group, as in GNOME Settings. A colour scale has one row per breakpoint, with a number and a colour button.
21. **Colour scales follow one rule.** Every sensor whose value is a number can have a colour scale, in every category; upstream allows one kind of value per category (for memory only the percentages) and none for voltage, network or storage. A scale is either for one sensor or for all sensors of a category that show the same kind of value. Where low values are the bad ones, such as free memory or a battery's charge, the colour applies below a breakpoint instead of above it. A breakpoint shows its unit, and sizes, frequencies and speeds have one fixed unit each (GiB, GHz, MB/s). No open issue of upstream asks for this.
22. **Icons can be themed and follow the value.** Every icon is taken by name from the user's icon theme, so a theme can replace any of them; upstream loads its own files. The WiFi values show signal bars, with GNOME's own icons at the same steps as GNOME's network indicator. The public IP shows its country's code in a monochrome icon that matches the others; upstream shows a coloured flag, which a setting switches off. That setting is gone, and a theme can bring the flags back.
23. **The public IP needs no choice of service.** The address and its country are looked up at Cloudflare, and at GeoJS and then country.is when a service does not answer within 3 seconds. Upstream asks one of three services, which the user picks; when that one is down, the address is gone until the user picks another. That setting is gone. After a lookup in which no service answered, the next tick tries again instead of waiting out the interval.
24. **Screen Redraws instead of a refresh rate.** The GPU value counts how many frames GNOME Shell draws per second, and is now called that: "Screen Redraws". It reveals a window that keeps redrawing without visibly changing, such as a terminal that animates a waiting icon. Upstream calls the same count "Refresh Rate", which it is not: the screen's refresh rate stays at, say, 60 Hz, while this count falls to almost nothing on a still screen. Here the count costs one addition per frame; upstream measures the time between frames.
25. **Less than half the CPU in the default setup.** With the menu closed and the three sensors a new user starts with in the top bar, the Shell spends 7.0 ms of CPU per second with this version and 16.3 ms with upstream, at a one-second interval; 2.7 ms of that is the Shell itself. Upstream's tracker has several reports of CPU load, lag and battery drain (#533, #260, #250, #150). With more sensors pinned or the menu open, this version is not faster; see "Speed and memory, measured" in part 2.

## Part 2: Under the hood

### What changed in the code

- **Size.** Outside tests, documents and translations: 21 files changed, about 3,250 lines added and 4,200 removed. `sensors.js`, `extension.js` and `prefs.js` are rewritten, `values.js` is replaced by `formatter.js`, and the UI file of the preferences and the three helper files for files, subprocesses and bytes are gone. The JavaScript is the same size as before (about 3,700 lines); the UI file's 994 lines have no replacement.
- **Tests.** Upstream has none, and its tracker has at least six reports of freezes, crashes and CPU spikes (#533, #286, #260, #250, and the open #542 and #582). This version has 60 unit tests. Those of the collector run it unchanged, with nothing in it replaced, on a test machine that stands in for `/sys`, `/proc`, the mounted filesystems, the public IP services, and the clock with its timers, so that no test waits out a second or an interval. A test inside a headless GNOME Shell uses the extension as a user does, with a virtual pointer and keyboard: the menu, the top bar, a real drag and the preferences window.
- **One catalog.** Every known sensor, the category switches and the panel are saved in one setting, `catalog`, not in ten `show-*` settings and `hot-sensors`. `sensors.js` reads the sensors and alone writes the catalog; `extension.js` displays it and changes only the row or top-bar item whose value changed. The design is in `docs/catalog-design.md`.
- **Failed reads.** Upstream ignores a failed read (26 empty `catch` blocks in `sensors.js`). Here it marks the sensor as unavailable and is written to the journal only with debug output on.
- **Storage space** is asked from GLib in the background; upstream's `libgtop` calls run on the Shell's main thread. The drives mounted by GNOME are the mounts of `Gio.VolumeMonitor`.
- **Batteries** are found by the type the kernel gives them (`type` is `Battery`), also those of a mouse or a keyboard, and the thermal zones come from `/sys/class/thermal`, without those that hwmon already covers. As UPower does, a battery's power rate takes its size from the driver and its sign from the battery's status, since drivers disagree on the sign.
- **Why upstream's unsorted rows have no order.** With sorting off, upstream inserts a row at a position computed from the number of properties of the row object (`extension.js`, `_appendMenuItem`).
- **Preferences.** The window is written in code with libadwaita's own rows and sidebar, one line per setting, and has no UI file; upstream's is a UI file of 994 lines plus a loop per kind of widget. The colour scales are drawn from the saved breakpoints; the preferences code went from 934 lines to under 400. The window no longer runs its own hardware discovery. The sidebar is a libadwaita element that exists since GNOME 50, which is why older versions are not supported.

### Speed and memory, measured

Measured on 2026-10-08 on one ThinkPad, in a headless GNOME Shell 50 with a 1280×720 screen and a one-second update interval. The numbers are the CPU time of the whole Shell process per second, averaged over two runs of 30 seconds each, taken back to back, and its memory after start. Single runs differ by about 2 ms.

| | No extension | Upstream | This version |
|---|---|---|---|
| Menu closed, default panel (3 sensors) | 2.7 ms | 16.3 ms | 7.0 ms |
| Menu closed, 8 sensors pinned, among them the temperature and fan averages | | 21.8 ms | 24.0 ms |
| Menu open, all categories closed | | 25.2 ms | 26.7 ms |
| Menu open, temperature category open | | 26.0 ms | 30.5 ms |
| Memory (resident) | 216 MB | 244 to 261 MB | 249 to 263 MB |

- In the default setup this version uses less than half of upstream's CPU time.
- With the temperature average on screen, this version is 2 to 4 ms per second slower. The cause is the six thermal zones it reads and upstream does not ("More sensors" in part 1): five of them ask the firmware on every read, which costs about 0.7 ms of CPU each in the kernel. With the thermal zones left out, the same measurement with 8 sensors pinned gives 22.0 ms for this version and 25.4 ms for upstream.
- What a read costs depends on the file, measured with 300 reads each: a `/proc` file or a `coretemp` temperature about 0.05 ms, an NVMe or ThinkPad temperature 0.25 to 0.5 ms, a thermal zone that asks the firmware 0.7 to 0.8 ms, a ThinkPad fan 0.8 to 1.1 ms. With 8 sensors pinned, the reads are about 18 of the 24 ms, and drawing the values about 3.
- Not measured: other machines, other intervals, a real desktop session with a graphics card.
