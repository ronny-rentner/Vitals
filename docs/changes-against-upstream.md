# How this fork differs from upstream Vitals

[Documentation index](../README.md) · [Screenshots](screenshots/README.md) · [Development](development.md)

We compared our `catalog-rewrite` working tree, including the translation and shutdown fixes, with upstream [`develop`](https://github.com/corecoding/Vitals/tree/c8c63ed) on 2026-10-31. The performance measurements date from 2026-10-08; we have not repeated them for these versions.

## Part 1: For the user

### User-visible differences

We ordered these changes using the issue references and reaction/comment counts collected on 2026-10-08. We have not rechecked those issues or counts. For the code comparison, we fetched upstream `develop` on 2026-10-31.

1. **The pinned sensors in the top bar can be reordered by drag and drop.** Drag a pinned sensor to its new position. Upstream keeps sensors in the order you pinned them; people in the feature request describe editing the setting by hand to change that order. Unpinning and repinning a sensor puts it at the end. This addresses [#93](https://github.com/corecoding/Vitals/issues/93) "Reorder indicators" (46), the most supported request in the October 8 count.
2. **Several storage locations.** The menu can show filesystem space for several disks and network shares, each in its own section, along with disk read and write rates. Choose mounted locations in preferences; `/` is monitored by default. Vitals shows readings whenever something is mounted at a configured path. You can also enable automatic monitoring of drives mounted by GNOME, such as USB sticks, while they are plugged in. Network shares have a separate polling interval in minutes. Vitals queries them only while mounted, so opening the menu does not connect an unmounted share. Upstream shows one filesystem, selected by entering a path in preferences. This addresses [#143](https://github.com/corecoding/Vitals/issues/143) "Multiple Storage Locations" (40), with [#455](https://github.com/corecoding/Vitals/issues/455) and [#503](https://github.com/corecoding/Vitals/issues/503).
3. **The menu's categories can be reordered.** In Menu preferences, set Order to Manual and enable Reorder by drag and drop. Drag a category header onto another to move it to that position. The preferences pages follow the same order. Upstream's category order is fixed. See [Using Vitals](../README.md#using-vitals). This addresses [#451](https://github.com/corecoding/Vitals/issues/451) "Order Menu Components" (25).
4. **NVIDIA polling stops when its readings are not needed.** The continuous `nvidia-smi` process runs only when the top bar or open menu needs an NVIDIA reading, including readings used in an aggregate. Discovery also queries the card. Upstream keeps the process running whenever GPU monitoring is enabled. Related requests: [#275](https://github.com/corecoding/Vitals/issues/275) "Check if dGPU is awake before polling" (11) and [#442](https://github.com/corecoding/Vitals/issues/442) "Option Monitor GPU prevents NVIDIA from going to sleep" (6). Our tests use a stand-in process. They do not tell us whether a real card sleeps between reads.
5. **Polling follows the top bar and menu.** Regular collection reads the sources needed by pinned sensors, category headers in the open menu, rows in expanded categories and their aggregates. Discovery makes additional reads to identify sensors. Upstream reads every menu value when the menu opens and the counters behind its rates on every tick, even when they are not shown. That gives upstream recent samples when the menu opens. Without recent samples, you'll see "…" until a second reading, scheduled one second after the first, arrives.
6. **Sensors can be renamed, hidden and shown in the category header.** Click a sensor row to open its actions: Pin to top bar, Pin to category, Rename and Hide. The row menu looks like the second-level menus in GNOME's quick settings. Hiding a sensor also excludes it from the average, minimum and maximum, so a bad reading no longer distorts them. Upstream has no rename, hide or category-pin actions. This addresses [#83](https://github.com/corecoding/Vitals/issues/83) "Customize labels" (14) and [#222](https://github.com/corecoding/Vitals/issues/222) "Hide unwanted sensors" (8).
7. **Network totals count hardware interfaces.** Traffic that also passes through a bridge, container or VPN is counted once, rather than across every interface ([#377](https://github.com/corecoding/Vitals/issues/377) and [#319](https://github.com/corecoding/Vitals/issues/319)). One sensor combines download and upload ([#198](https://github.com/corecoding/Vitals/issues/198)). The menu hides virtual interfaces by default, with an option to show them. Upstream now removes vanished interfaces too, so we no longer count that as a difference.
8. **Storage monitoring does not need libgtop.** We query filesystem space through GLib. Upstream requires `libgtop` and shows no storage readings without it. Its README lists installation commands for each distribution; [#421](https://github.com/corecoding/Vitals/issues/421) concerns the Arch instructions. See [Installation](../README.md#installation) for the build dependencies.
9. **Icons can keep their original proportions.** Top-bar icons can be cropped to remove transparent borders while preserving their aspect ratio, symbolic recolouring and theme support. Menu icons keep GNOME's stock sizing. Upstream adjusts the gap between icons and values with margins measured from each category's SVG in each icon style. We use cropped icons and shared spacing rules.
10. **Unavailable sensors disappear until readings resume.** Upstream disables the row but keeps showing its last value. We also exclude unavailable temperatures from the average, minimum and maximum while keeping the other readings.
11. **Voltages are not mixed.** We removed the voltage average, minimum and maximum. Upstream calculates them across unrelated voltages, such as a 17 V battery, a 1.2 V rail and a 5 V USB supply. The category header prefers the battery's voltage, then the system's, and uses a USB supply's voltage only if neither is available. Related request: [#381](https://github.com/corecoding/Vitals/issues/381) "PSU Voltage contaminating Voltage monitoring".
12. **Batteries are discovered automatically.** Each computer or peripheral battery has its own readings. Mouse and keyboard batteries use their device's name. When the computer has several batteries, their power rates are added together; peripheral batteries are excluded from that total. All UPS devices reported by UPower are discovered too. Upstream lets you select one of eight named battery slots or one UPS through UPower. Both versions apply a discharge sign to battery power; we first normalize the sign reported by the driver. We apply "Skip sensors that read zero" only to temperatures, so an idle voltage sensor stays available. Related requests: [#263](https://github.com/corecoding/Vitals/issues/263) and [#540](https://github.com/corecoding/Vitals/issues/540).
13. **Top-bar widths can be remembered.** "Emphasize values" makes icons and units lighter and smaller than the numbers. "Steady widths" releases unused space after a minute, and "Remember widths" restores each value's saved width after a restart. Turn steady widths off to let the text use its natural width. Upstream reserves a minimum width at first and keeps enough space for the widest value until it rebuilds the top-bar items. It does not save those widths between sessions. We leave digit shaping to the Shell theme.
14. **The menu has a fixed width and opening position.** By default, it opens centered under the pointer and stays there while open. An option centers it under the pinned sensors instead. Upstream sizes the menu to its widest row and positions it relative to the combined width of the pinned sensors, within the screen edges. Our menu also remembers which category was open when you closed it. Short categories and categories with a scrollbar use the same opening animation.
15. **Related rows stay together.** Sections and headings group readings. The memory breakdown has an explicit row order; other rows sort by their translated labels. Upstream has an alphabetical sorting switch. When it is off, a row's insertion position depends on the number of properties on its row object.
16. **The network category is divided into sections.** Machine totals, hardware interfaces, transferred amounts and optional virtual interfaces are separate. An interface name appears once as a heading, such as "WiFi (wlp0s20f3)"; its rows say "Download speed" and "Upload speed". Upstream lists "wlp0s20f3 rx", "Device rx", "Boot rx" and "Session rx" in one list. Temperature and fan aggregates also have their own section and can be hidden.
17. **Pins and colours use sensor keys.** Renaming a sensor changes its label while preserving its pin and colour rule. Upstream derives keys from labels and has no rename action. Our keys can still refer to a different physical device if identical devices are discovered in a different order.
18. **Units are written the standard way.** `kB`, `kHz` and `kbit/s`: a lowercase k for a thousand, and a slash in data-transfer rates. Upstream writes `KB`, `KHz` and, for bits, `Kbps`, next to `KB/s` for bytes.
19. **More readings, with hardware rediscovery.** We added thermal zones not already covered by hwmon, a processor power-limit reading and ThinkPad lap mode. Generic hwmon devices with identical names get numbered keys. Opening the menu runs hardware discovery again. Upstream refreshes its network discovery but keeps the results of its initial hwmon discovery. Both versions support individual CPU cores, live cpufreq readings with a cpuinfo fallback, hwmon power readings and power readings calculated from powercap energy counters.
20. **Preferences offer fixed choices for the update interval.** You choose from eight values instead of using upstream's slider from 1 to 60. Settings with a few choices use toggle groups. Each colour-scale breakpoint has its own row with a number and a colour button.
21. **Colour scales cover more kinds of readings.** You can set colour scales for numeric readings in every category, applying them to one sensor or a kind of value. Upstream supports temperature, fan speed, memory/processor/GPU percentages, system load and battery percentage. For readings where low values are a concern, such as free memory, the colour applies below the threshold. Each breakpoint shows the unit used for its comparison.
22. **Icons follow the theme and the reading.** We look up sensor icons by name in your icon theme. Upstream loads its own files. WiFi icons show signal bars using GNOME's signal-strength thresholds. The public IP uses a monochrome country-code icon. Upstream uses a coloured flag with a separate switch to show or hide it; we use country-code icons without a flag option.
23. **Public IP lookups have automatic fallback.** We look up the address and country through Cloudflare, then try GeoJS and country.is if a service does not answer within 3 seconds. If none answers, we retry on the next tick instead of waiting for the polling interval. Upstream uses one service that you choose in preferences and retries it at the configured interval. It has no automatic fallback. We removed the service-selection setting.
24. **The frame counter is called Screen Redraws.** This GPU reading counts how many frames GNOME Shell draws per second. It can reveal a window that keeps redrawing without visibly changing, such as a terminal with an animated waiting icon. Upstream calls this count "Refresh Rate". A screen can keep refreshing at 60 Hz while GNOME draws almost no new frames, so we call it "Screen Redraws". We increment a counter once per frame; upstream measures the time between frames.
25. **The memory breakdown adds up.** Free + Reclaimable = Available, and Used + Available = Total, even after rounding for display. "Show details" adds a separate section for file cache, shared memory, kernel cache, buffers and usage. Swap has its own section. Upstream lists Available, Allocated, Cached and Free together without a Reclaimable row to explain how they add up.
26. **Translations cover the current messages.** All 22 existing language catalogs contain the 266 messages in the current template, with no empty or fuzzy entries. The compiled catalogs are up to date too. We filled in the missing translations for new labels and descriptions.

### What is lost or worse

- **You'll need GNOME Shell 50 or 51.** We use newer APIs for the preferences sidebar and cropped icons. Upstream also supports GNOME 45 to 49.
- **You'll need to set up your pins again when switching.** We identify sensors independently of their labels, so settings that use upstream's identifiers do not carry over. Review your other preferences too; see [Installation](../README.md#installation).
- **Preferences can show stale sensor lists after rediscovery.** The collector does not save discovery changes when the sensor count stays the same. See the [catalog persistence bug](catalog-design.md#on-disk).

## Part 2: Under the hood

### What changed in the code

- **Structure.** We rewrote `sensors.js`, `extension.js` and `prefs.js`. `formatter.js` replaces `values.js`; the preferences UI file and the file, subprocess and byte helpers are gone. The collector stores source state separately from the saved sensor catalog. Cropping is isolated in `croppedIcon.js`.
- **Tests.** We have 71 unit tests and 15 Shell checks; upstream has no test suite in its tree. Collector tests run against a simulated machine providing files, mounted filesystems, public-IP responses and timers. The Shell checks exercise the real UI with a virtual pointer and keyboard. Branches and pull requests run the unit tests in CI; release tags additionally package, validate and publish the extension.
- **Catalog and settings.** The `catalog` setting stores sensors, readings, pins, labels and ordering. `catalog-settings` separately stores category on/off switches. The collector owns the catalog; the renderer updates the affected rows and top-bar items. Upstream uses `show-*` settings, `hot-sensors` and separate reading histories. See [catalog design](catalog-design.md).
- **Failed reads.** The collector marks readings unavailable and logs the first failure in a sequence at debug level. Upstream ignores many read failures; hwmon failures disable an existing row while retaining its last displayed value.
- **Storage space** is queried asynchronously through GLib; upstream's `libgtop` calls run on the Shell's main thread. Drives mounted by GNOME are reported by `Gio.VolumeMonitor`.
- **Batteries** are discovered from power supplies whose kernel `type` is `Battery`, including mouse and keyboard batteries. A battery's power rate uses the magnitude reported by the driver and the sign determined from its charging status, since drivers disagree on the sign.
- **Thermal zones** come from `/sys/class/thermal`, excluding those already covered by hwmon.
- **Shutdown.** The button's destruction signal saves the catalog, stops the timer and destroys the collector, including when Shell exits without calling the extension's `disable()`. Pending read completions are discarded. Upstream guards callbacks after its JavaScript `destroy()` method clears the collector reference.
- **Row ordering.** With alphabetical sorting off, upstream's `_appendMenuItem` computes the insertion position from the number of properties on the row object. We sort rows by section, heading, explicit order and displayed label.
- **Preferences.** We build the window in JavaScript with libadwaita rows and `Adw.ViewSwitcherSidebar`. Upstream combines JavaScript with a UI file and connects sidebar navigation manually. Our preferences read the saved catalog rather than running hardware discovery. The catalog's [persistence bug](catalog-design.md#on-disk) can leave those sensor lists stale until another save.

### Historical speed and memory measurements

We measured earlier versions of both branches on 2026-10-08. These results cannot tell us which branch is faster today. We used one ThinkPad running a headless GNOME Shell 50, with a 1280×720 screen and a one-second update interval. CPU time covers the whole Shell process, measured per second and averaged over two consecutive 30-second runs. We measured memory after startup. Individual runs differed by about 2 ms.

| | No extension | Earlier upstream | Our earlier version |
|---|---|---|---|
| Menu closed, default panel (3 sensors) | 2.7 ms | 16.3 ms | 7.0 ms |
| Menu closed, 8 sensors pinned, among them the temperature and fan averages | | 21.8 ms | 24.0 ms |
| Menu open, all categories closed | | 25.2 ms | 26.7 ms |
| Menu open, temperature category open | | 26.0 ms | 30.5 ms |
| Memory (resident) | 216 MB | 244 to 261 MB | 249 to 263 MB |

- Our earlier version used less than half of upstream's CPU time in the default setup.
- With the temperature average on screen, our earlier version was 2 to 4 ms per second slower. At the time, we attributed this to six extra thermal zones, five of which queried the firmware on each read. With those zones excluded, the eight-sensor measurement was 22.0 ms for our version and 25.4 ms for upstream.
- The recorded 300-read samples cost about 0.05 ms of CPU per `/proc` or coretemp read, 0.25 to 0.5 ms for NVMe or ThinkPad temperatures, 0.7 to 0.8 ms for firmware thermal zones, and 0.8 to 1.1 ms for the ThinkPad fan. With eight sensors pinned, reads accounted for about 18 of 24 ms, and rendering about 3 ms.
- We did not measure other machines, other intervals or a real desktop session with a graphics card.
