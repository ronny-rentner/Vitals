# What this version changes against upstream Vitals

[Documentation index](../README.md) · [Screenshots](screenshots/README.md) · [Development](development.md)

Compared on 2026-10-31: upstream [`develop`](https://github.com/corecoding/Vitals/tree/c8c63ed) and the `catalog-rewrite` working tree, including the translation and shutdown fixes. Performance measurements below are from 2026-10-08 and have not been repeated for these versions.

## Part 1: For the user

### User-visible differences

Issue references and reaction/comment counts were collected on 2026-10-08. They explain the original ordering; their current status and counts have not been rechecked. The code comparison uses the upstream `develop` fetched on 2026-10-31.

1. **The pinned sensors in the top bar can be reordered by drag and drop.** The user drags a sensor in the top bar to where it should be. Upstream shows pinned sensors in the order they were pinned, and people in the request edit the setting by hand. Repinning a sensor appends it to the panel. Answers [#93](https://github.com/corecoding/Vitals/issues/93) "Reorder indicators" (46), the most supported request in the October 8 count.
2. **Several storage locations.** The menu shows filesystem space for several disks and network shares, each in its own section, plus disk read and write rates. Upstream shows one filesystem, the one containing a path entered in preferences. Here, the preferences window lists mounted locations to choose from; `/` is monitored by default. A configured location has values whenever something is mounted there. One switch also includes drives mounted by GNOME, such as USB sticks, while they are plugged in. Network shares have a separate polling interval, in minutes, and are queried only while mounted; opening the menu does not connect an unmounted share. Answers [#143](https://github.com/corecoding/Vitals/issues/143) "Multiple Storage Locations" (40), with [#455](https://github.com/corecoding/Vitals/issues/455) and [#503](https://github.com/corecoding/Vitals/issues/503).
3. **The menu's categories can be reordered.** With Menu › Order set to Manual and dragging enabled, a category dragged onto another takes its place. Preferences follows the same order. Upstream's order is fixed. See [Using Vitals](../README.md#using-vitals). Answers [#451](https://github.com/corecoding/Vitals/issues/451) "Order Menu Components" (25).
4. **NVIDIA polling stops when its readings are not needed.** The continuous `nvidia-smi` process runs while an NVIDIA reading is needed in the top bar or open menu, including as an aggregate input. Discovery also queries the card. Upstream keeps its monitoring process running while GPU monitoring is enabled. Related requests: [#275](https://github.com/corecoding/Vitals/issues/275) "Check if dGPU is awake before polling" (11) and [#442](https://github.com/corecoding/Vitals/issues/442) "Option Monitor GPU prevents NVIDIA from going to sleep" (6). Process handling is tested with a stand-in; whether a real card sleeps between reads has not been tested.
5. **Polling follows the top bar and menu.** Regular collection reads sources needed by pinned sensors, category headers in the open menu, rows in expanded categories and their aggregates. Discovery performs additional reads to identify sensors. Upstream reads every menu value when the menu opens, and the counters behind its rates on every tick, whether shown or not. The tradeoff is a delay: a rate whose source has no fresh samples shows "…" until its second reading, scheduled one second later. Upstream already has samples when the menu opens.
6. **Sensors can be renamed, hidden and shown in the category header.** A click on a row opens its actions: Pin to top bar, Pin to category, Rename and Hide. They look like the second-level menus of GNOME's quick settings. A hidden sensor is also left out of the average, minimum and maximum, so one that reads nonsense no longer spoils them. Upstream has no rename, hide or category-pin actions. Answers [#83](https://github.com/corecoding/Vitals/issues/83) "Customize labels" (14) and [#222](https://github.com/corecoding/Vitals/issues/222) "Hide unwanted sensors" (8).
7. **Network totals count hardware interfaces.** Traffic that also passes through a bridge, container or VPN is counted once, rather than across every interface ([#377](https://github.com/corecoding/Vitals/issues/377) and [#319](https://github.com/corecoding/Vitals/issues/319)). One sensor combines download and upload ([#198](https://github.com/corecoding/Vitals/issues/198)). The menu hides virtual interfaces by default, with an option to show them. Both versions now remove vanished interfaces; this is no longer a difference from upstream.
8. **Storage monitoring needs no libgtop package.** This version queries filesystem space through GLib. Upstream needs `libgtop` for it, shows nothing without it, and its README lists distribution-specific installation commands; [#421](https://github.com/corecoding/Vitals/issues/421) concerns those instructions for Arch. The fork's build dependencies are listed under [Installation](../README.md#installation).
9. **Icons can be cropped to their proportions.** The top bar removes transparent borders while retaining the artwork’s aspect ratio, symbolic recolouring and theme support. The menu keeps stock icon sizing. Upstream now equalizes icon-to-value gaps with per-style, per-category margins measured from its SVG files; this version uses cropped icons and shared spacing rules.
10. **Unavailable sensors are not displayed.** A sensor that cannot be read disappears until readings resume; upstream's row keeps showing its last value, disabled. Unavailable temperatures are excluded from the average, minimum and maximum without discarding the other readings.
11. **Voltages are not mixed.** The voltage category no longer has an average, minimum and maximum over all voltages; upstream's put a 17 V battery, a 1.2 V rail and a 5 V USB supply into one number. The category header shows the battery's voltage, else the system's, and a USB supply's only when there is nothing else. Relates to [#381](https://github.com/corecoding/Vitals/issues/381) "PSU Voltage contaminating Voltage monitoring".
12. **Batteries are discovered automatically.** Each machine and peripheral battery gets its own readings; a mouse or keyboard battery is named after its device. Multiple machine batteries have a combined power rate that excludes peripheral batteries. Upstream selects one of eight named battery slots, or one UPS through UPower. This version discovers all UPower UPS devices alongside the other batteries. Both versions apply a discharge sign to battery power; this version normalizes the driver’s sign first. “Skip sensors that read zero” applies only to temperatures here, so an idle voltage sensor remains available. Related requests: [#263](https://github.com/corecoding/Vitals/issues/263) and [#540](https://github.com/corecoding/Vitals/issues/540).
13. **Top-bar widths can be remembered.** “Emphasize values” draws icons and units lighter and smaller than the numbers. “Steady widths” releases unused room after a minute; “Remember widths” restores each value’s saved width after restart. Turning steady widths off uses the text’s natural width. Upstream reserves a minimum initial width and retains the widest value until its panel items are rebuilt; it does not save those widths between sessions. Digit shaping follows the Shell theme here.
14. **The menu has a fixed width and opening position.** It opens centered under the pointer and stays there while open; an option centers it under the sensors instead. Upstream's width follows its widest row, and its position follows the combined width of its pinned sensors, subject to the screen edges. This version also remembers the open category while the menu is closed and uses the same opening animation for short and scrolling categories.
15. **Rows have a defined order.** Sections and headings group related readings. Explicit row order keeps the memory breakdown together; remaining rows sort by their translated labels. Upstream offers an alphabetical switch; with it off, insertion uses the number of properties on a row object.
16. **The network category is divided into sections.** Machine totals, hardware interfaces, transferred amounts and optional virtual interfaces are separate. An interface name appears once as a heading, such as “WiFi (wlp0s20f3)”; its rows say “Download speed” and “Upload speed”. Upstream lists “wlp0s20f3 rx”, “Device rx”, “Boot rx” and “Session rx” in one list. Temperature and fan aggregates also have their own section and can be hidden.
17. **Pins and colours use sensor keys.** Renaming a sensor changes its label, not its pin or colour rule. Upstream derives keys from labels and has no rename action. Keys here still do not guarantee physical-device identity when identical devices change discovery order.
18. **Units are written the standard way.** `kB`, `kHz` and `kbit/s`: a lowercase k for a thousand, and a slash in data-transfer rates. Upstream writes `KB`, `KHz` and, for bits, `Kbps`, next to `KB/s` for bytes.
19. **Additional readings and rediscovery.** This version adds thermal zones not already represented by hwmon, a processor power-limit reading and ThinkPad lap mode. Generic hwmon devices with identical names get numbered keys. Hardware is rediscovered when the menu opens; upstream refreshes network discovery but retains its initial hwmon discovery. Both versions now offer individual CPU cores, live cpufreq readings with a cpuinfo fallback, hwmon power and powercap energy-based power readings.
20. **Preferences use discrete controls.** The update interval is picked from eight values instead of upstream's slider from 1 to 60. Small sets of choices use toggle groups. A colour scale has one row per breakpoint, with a number and a colour button.
21. **Colour scales cover more kinds of readings.** This version supports scales for numeric readings across all categories, targeting either one sensor or a kind of value. Upstream supports temperature, fan speed, memory/processor/GPU percentages, system load and battery percentage. Here, a low-is-bad reading such as free memory applies its colour below the threshold. Breakpoints display the unit used for their comparison.
22. **Icons can be themed and follow the value.** Sensor icons are looked up by name in the user's icon theme; upstream loads its own files. WiFi readings show signal bars at GNOME's signal-strength thresholds. The public IP uses a monochrome country-code icon. Upstream uses a coloured flag with a separate visibility switch; this version has no flag option.
23. **The public IP needs no choice of service.** The address and its country are looked up at Cloudflare, and at GeoJS and then country.is when a service does not answer within 3 seconds. Upstream uses one user-selected service and retries it at the configured interval; it has no automatic provider fallback. That setting is gone. After a lookup in which no service answered, the next tick tries again instead of waiting out the interval.
24. **Screen Redraws instead of a refresh rate.** The GPU value counts how many frames GNOME Shell draws per second, and is now called that: "Screen Redraws". It reveals a window that keeps redrawing without visibly changing, such as a terminal that animates a waiting icon. Upstream calls the same count "Refresh Rate", which it is not: the screen's refresh rate stays at, say, 60 Hz, while this count falls to almost nothing on a still screen. Here the count costs one addition per frame; upstream measures the time between frames.
25. **The memory breakdown adds up.** Free + Reclaimable = Available, and Used + Available = Total, including at the displayed precision. “Show details” adds a separate section for file cache, shared memory, kernel cache, buffers and usage; swap has its own section. Upstream lists Available, Allocated, Cached and Free together without a reclaimable row that reconciles them.
26. **Translations cover the current messages.** All 22 existing language catalogs contain the 266 messages in the current template, with no empty or fuzzy entries. The compiled catalogs are updated too. The earlier limitation that new labels and descriptions fell back to English has been resolved.

### Requests this version does not address

- [#314](https://github.com/corecoding/Vitals/issues/314) "Make indicator configuration more discoverable" (17).
- [#426](https://github.com/corecoding/Vitals/issues/426) and [#366](https://github.com/corecoding/Vitals/issues/366), icons per temperature sensor (17 together).

### What is lost or worse

- **GNOME 45 to 49 are no longer supported.** Upstream lists 45 to 51. This version lists 50 and 51.
- **Old sensor configurations are not migrated.** Switching from upstream requires setting up pins again and checking preferences; see [Installation](../README.md#installation).
- **Preferences can show stale sensor lists after rediscovery.** The collector does not save discovery changes when the sensor count stays the same. See the [catalog persistence bug](catalog-design.md#on-disk).

## Part 2: Under the hood

### What changed in the code

- **Structure.** `sensors.js`, `extension.js` and `prefs.js` are rewritten. `formatter.js` replaces `values.js`; the preferences UI file and the file, subprocess and byte helpers are gone. The collector stores source state separately from the saved sensor catalog. Cropping is isolated in `croppedIcon.js`.
- **Tests.** This version has 71 unit tests and 15 Shell checks; upstream has no test suite in its tree. Collector tests run against a simulated machine providing files, mounted filesystems, public-IP responses and timers. The Shell checks exercise the real UI with a virtual pointer and keyboard. Branches and pull requests run the unit tests in CI; release tags additionally package, validate and publish the extension.
- **Catalog and settings.** The `catalog` setting stores sensors, readings, pins, labels and ordering. `catalog-settings` separately stores category on/off switches. The collector owns the catalog; the renderer updates the affected rows and top-bar items. Upstream uses `show-*` settings, `hot-sensors` and separate reading histories. See [catalog design](catalog-design.md).
- **Failed reads.** This version marks unavailable readings and logs the first failure in a sequence at debug level. Upstream ignores many read failures; hwmon failures disable an existing row while retaining its last displayed value.
- **Storage space** is queried asynchronously through GLib; upstream's `libgtop` calls run on the Shell's main thread. Drives mounted by GNOME are reported by `Gio.VolumeMonitor`.
- **Batteries** are discovered from power supplies whose kernel `type` is `Battery`, including mouse and keyboard batteries. A battery's power rate uses the magnitude reported by the driver and the sign determined from its charging status, since drivers disagree on the sign.
- **Thermal zones** come from `/sys/class/thermal`, excluding those already covered by hwmon.
- **Shutdown.** The button's destruction signal saves the catalog, stops the timer and destroys the collector, including when Shell exits without calling the extension's `disable()`. Pending read completions are discarded. Upstream guards callbacks after its JavaScript `destroy()` method clears the collector reference.
- **Row ordering.** With alphabetical sorting off, upstream's `_appendMenuItem` computes the insertion position from the number of properties on the row object. This version sorts by section, heading, explicit order and displayed label.
- **Preferences.** This version builds the window in JavaScript with libadwaita rows and `Adw.ViewSwitcherSidebar`. Upstream combines JavaScript with a UI file and connects sidebar navigation manually. The preferences here read the saved catalog rather than running hardware discovery; its [persistence bug](catalog-design.md#on-disk) can leave their sensor lists stale until another save.

### Historical speed and memory measurements

These measurements were recorded on 2026-10-08 against the earlier upstream baseline, before the current implementations. They do not establish which current branch is faster. They used one ThinkPad, a headless GNOME Shell 50, a 1280×720 screen and a one-second update interval. CPU time is for the whole Shell process per second, averaged over two consecutive 30-second runs; memory was measured after startup. Single runs differed by about 2 ms.

| | No extension | Earlier upstream | Earlier fork |
|---|---|---|---|
| Menu closed, default panel (3 sensors) | 2.7 ms | 16.3 ms | 7.0 ms |
| Menu closed, 8 sensors pinned, among them the temperature and fan averages | | 21.8 ms | 24.0 ms |
| Menu open, all categories closed | | 25.2 ms | 26.7 ms |
| Menu open, temperature category open | | 26.0 ms | 30.5 ms |
| Memory (resident) | 216 MB | 244 to 261 MB | 249 to 263 MB |

- In that measurement, the fork used less than half of upstream’s CPU time in the default setup.
- With the temperature average on screen, the fork was 2 to 4 ms per second slower. The recorded analysis attributed this to six extra thermal zones, five of which asked the firmware on each read. With those zones excluded, the eight-sensor measurement was 22.0 ms for the fork and 25.4 ms for upstream.
- The recorded 300-read samples cost about 0.05 ms of CPU per `/proc` or coretemp read, 0.25 to 0.5 ms for NVMe or ThinkPad temperatures, 0.7 to 0.8 ms for firmware thermal zones, and 0.8 to 1.1 ms for the ThinkPad fan. With eight sensors pinned, reads accounted for about 18 of 24 ms, and rendering about 3 ms.
- Not measured: other machines, other intervals, a real desktop session with a graphics card.
